# Архитектура управляемых VLESS-соединений

## 1. Цель

Mors управляет одним глобальным списком из одного-четырёх равноправных VLESS Reality соединений. Одно соединение активно, остальные исправные соединения являются резервами. Смена активного соединения происходит только после подтверждённого сбоя или явного действия пользователя.

## 2. Неподвижные внешние границы

- Один процесс Xray.
- Один основной SOCKS inbound на `127.0.0.1:1097`.
- Один системный Proxy-интерфейс Keenetic.
- Одна точка интеграции с существующей NDM и iptables маршрутизацией Mors.
- От одного до четырёх Xray outbound с неизменяемыми тегами на основе внутреннего ID.

Добавление соединения не создаёт отдельный процесс Xray или отдельный пользовательский Keenetic-интерфейс.

## 3. Компоненты

### 3.1 Реестр

Реестр является декларативным источником истины и содержит:

- `schema_version`;
- ревизию конфигурации;
- глобальную политику прямого резерва;
- глобальный признак паузы, не изменяющий выбор включённых соединений;
- основной и резервный контрольные адреса;
- список внутренних ID;
- уникальные пользовательские имена;
- признаки `enabled`;
- даты создания и обновления.

Чувствительные VLESS-параметры хранятся в отдельных файлах с правами `600`. Исходный URI после успешного разбора не сохраняется.

### 3.2 Генератор Xray

Генератор строит `/opt/etc/xray/mors.json` из реестра и файлов соединений. Ручное редактирование сгенерированного файла не поддерживается.

Конфигурация включает:

- основной SOCKS inbound;
- outbound каждого включённого соединения;
- routing balancer;
- Observatory;
- локальный Routing API;
- отдельный localhost-only диагностический SOCKS inbound для каждого включённого outbound;
- `direct` и `blackhole` outbound, между которыми supervisor выбирает по глобальной политике.

Любое изменение проходит стадии `parse -> validate -> generate candidate -> xray run -test -> atomic replace -> runtime apply`. Candidate и rollback-файлы сохраняют расширение `.json`, по которому Xray определяет формат. Ошибка на любой стадии сохраняет предыдущую рабочую ревизию.

### 3.3 Supervisor

Supervisor является отдельным Entware-сервисом. Он не генерирует конфигурацию в основном цикле и не перезапускает Xray при обычном автоматическом переключении.

Обязанности:

- выполнять HTTP-проверки через диагностический inbound каждого соединения и учитывать встроенный Observatory как дополнительную защиту data-plane;
- вести машину состояний соединений;
- выполнять подтверждающие проверки;
- отличать сбой VLESS от общей потери интернета;
- выбирать лучший исправный резерв;
- фиксировать outbound через локальный Routing API;
- сохранять последнее активное соединение;
- записывать структурированные события;
- восстанавливать выбор после перезагрузки.

Перед каждым health-cycle supervisor проверяет schema производного
`state.json`. Отсутствующий или повреждённый файл атомарно пересоздаётся из
реестра и сохранённого active preference без изменения credentials.

Только один экземпляр supervisor может принимать решения. Process lock защищает от двух supervisor, а общий decision lock сериализует полный health-cycle со всеми изменяющими CLI-операциями. Entware init управляет shell-процессом по защищённому PID-файлу supervisor и перед отправкой сигнала сверяет точный argv через `/proc`, поскольку стандартный `pidof` видит такой процесс только как `sh`. Интервальное ожидание supervisor использует секундные foreground-срезы: это исключает race BusyBox `ash` между background `sleep` и `wait`, `USR1` начинает новый health-cycle не позднее следующего среза, а `TERM` освобождает process lock и завершает сервис без ожидания полного интервала. Если BusyBox `ash` ждёт foreground probe и откладывает trap, init в пределах stop timeout повторно завершает только direct children с заново подтверждённым `PPid` этого supervisor. `status`, `list` и `events` не изменяют runtime state. Отдельный редкий watchdog проверяет наличие процесса и перезапускает сервис, но никогда не выбирает outbound.

## 4. Машина состояний

```text
disabled -> checking -> standby -> unstable -> unavailable
                |          |          |             |
                +-------- active -----+-------------+
                           |
                       draining
```

Правила:

1. После запуска восстанавливается последнее активное соединение со статусом `checking`.
   Routing API закрепляет его до начала последовательных проверок, чтобы `leastPing` не выполнил скрытый failback.
2. Один успешный первичный цикл подтверждает базовую доступность.
3. Первая ошибка переводит соединение в `unstable`.
4. Выполняются две быстрые повторные проверки через резервный endpoint.
5. Если общий интернет недоступен, supervisor фиксирует upstream-проблему и не перебирает VLESS-соединения бессмысленно.
6. Подтверждённый сбой переводит соединение в `unavailable`.
7. Среди `standby` выбирается кандидат с наиболее свежими успехами, меньшим числом недавних ошибок и лучшей сглаженной задержкой.
8. После переключения новый outbound остаётся активным до собственного сбоя. Автоматического возврата нет.
9. Восстановившееся старое соединение становится `standby`.
10. При ручном плавном выключении активное соединение становится `draining`. Новые сессии направляются в резерв, старые завершаются естественно.

## 5. Общая недоступность

- Если прямой резерв запрещён, маршрут остаётся закрытым и общий статус равен `unavailable`.
- Если прямой резерв явно разрешён, используется direct outbound и статус равен `direct_fallback`.
- Включение прямого резерва требует явного предупреждения и подтверждения.
- Если все соединения выключены пользователем или включена глобальная пауза, статус равен `paused`, проверки прекращаются.

## 6. Выбор резерва

Соединения не имеют ручного приоритета. Кандидат должен:

1. быть включён;
2. иметь свежий успешный результат;
3. не находиться в `unstable`, `unavailable` или `draining`;
4. иметь лучшую оценку здоровья.

Оценка использует дискретные признаки здоровья прежде задержки. Низкая задержка не компенсирует свежие ошибки. При равной оценке применяется стабильный детерминированный порядок по внутреннему ID, чтобы решение можно было воспроизвести.

## 7. Контрольные запросы

- В нормальном режиме используется один лёгкий HTTPS endpoint с ожидаемым ответом `204`.
- После ошибки выполняется проверка через второй независимый endpoint.
- При одновременном падении VLESS выполняется отдельная прямая проверка доступности интернета.
- Endpoint можно изменить в расширенных настройках.
- Диагностический запрос не отправляет UUID, ключи или пользовательские домены.

Конкретные интервалы и тайм-ауты являются именованными настройками с безопасными значениями по умолчанию и покрываются тестами с управляемыми часами.

## 8. Персистентность и события

Конфигурация и оперативное состояние разделены:

- `/opt/etc/mors/vless` содержит пользовательскую конфигурацию;
- `/opt/var/lib/mors/vless` содержит последнее выбранное VLESS-соединение для восстановления и ограниченную историю событий; это сохранённое предпочтение не считается текущим `active_id`, пока data-plane переведён в `direct_fallback` или fail-closed;
- `/opt/var/run/mors/vless` содержит только runtime-файлы.

Обычный uninstall сохраняет конфигурацию и историю. Успешный
`mors uninstall --purge --yes` после остановки supervisor и Xray удаляет все три
Mors-specific дерева и сгенерированные `/opt/etc/xray/mors.json*`, не затрагивая
системный init `/opt/etc/init.d/S24xray`.

`mors vless status|list` дополнительно ограничивает оперативное состояние
lifecycle-пакета: роли `active` и `standby` являются текущими только в `ready`
без active lifecycle marker. Незавершённая транзакция публикуется отдельно как
`lifecycle_transaction_active: true`, скрывает текущие роли и не меняет
сохранённый стабильный `lifecycle_state`.
В `unconfigured` включённые профили имеют состояние `not_configured`, а в
`recovery_required` — `unknown`; прежний health snapshot публикуется отдельно
как `last_runtime` и не выдаётся за работающий data-plane.

Системный runtime Xray использует `/opt/etc/init.d/S24xray`, принадлежащий
Entware-пакету `xray`; Mors не владеет этим файлом и не удаляет его при uninstall.
Managed exact symlink `/opt/etc/init.d/S97xray`, созданный предыдущими версиями,
сохраняется в snapshot, снимается при успешном apply и восстанавливается при
rollback. Внешний `S97xray` определяется до первой мутации setup, фиксируется как
`external` без копирования, никогда не изменяется rollback и блокирует VLESS activation во избежание
двух конкурирующих boot hooks. Lifecycle rollback до восстановления файлов
останавливает Xray и supervisor, затем подтверждает их отсутствие по процессам.
Восстановление исходно работающих сервисов считается успешным только после
проверки устойчивого poststate. Остановка уже `dead`/`stopped` процесса
идемпотентна; сырой exit code init-скрипта сохраняется для диагностики, но не
перевешивает подтверждённый desired state.

После успешного add/update/enable Mors до запуска Xray синхронизирует IP всех включённых endpoint в `MORS_DESTINATION_EXCLUDED`: сначала добавляет новые, затем удаляет только ранее управляемые VLESS-адреса.

Событие включает время, тип, предыдущее и новое соединение, безопасную причину и результат. История ротируется по размеру. Системный журнал получает краткую копию без секретов.

## 9. Версионирование и миграции

- Первая версия новой модели настраивается с нуля.
- Каждый сохранённый документ содержит `schema_version`.
- Последующие обновления обязаны мигрировать поддерживаемые схемы автоматически.
- Перед миграцией создаётся резервная копия.
- Миграция выполняется транзакционно и не удаляет исходные данные до проверки новой схемы.
- Неизвестная более новая схема не перезаписывается старой версией Mors.

## 10. Совместимость Xray

Observatory, диагностические SOCKS inbound и Routing API проверяются на минимальной и последней протестированной версиях Xray. Статическая проверка JSON недостаточна: CI должен запустить Xray, проверить диагностические inbound и выполнить принудительный выбор outbound.

Если минимальная версия не реализует требуемый runtime-контракт, минимальная поддерживаемая версия повышается после успешной CI-проверки. Перезапуск Xray при каждом failover не используется как скрытый compatibility fallback, потому что он разрывает пользовательские сессии и меняет согласованную семантику.

## 11. Границы ответственности

- `libs/vless` предоставляет доменные команды и не содержит бесконечный monitor-цикл.
- Хранилище не вызывает Xray API.
- Генератор не принимает решения о здоровье.
- Supervisor не парсит пользовательские URI и не редактирует конфигурацию.
- `libs/vpn` только выбирает VLESS как один из тоннелей Mors и не управляет отдельными VLESS outbound.
- NDM и firewall продолжают видеть один системный Proxy-интерфейс.

## 12. Release gates

До выпуска обязательны:

- тесты хранилища и транзакций;
- тесты машины состояний и flapping;
- runtime-тесты Xray API;
- проверка отсутствия секретов;
- проверка setup, backup, rollback и uninstall;
- статический QA и BATS;
- независимый code review субагентом;
- исправление замечаний и повторный полный QA;
- обновлённый `HISTORY.md` и русские release notes.
