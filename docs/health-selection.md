# Чистые health/selection в Rust (#70)

База: `main`, `400a2b44fa8d303c3007aaf638fa69a258cbcace` (27.09.2026).
Реализация находится в `mors-domain`: [health.rs](../crates/domain/src/health.rs),
[selection.rs](../crates/domain/src/selection.rs),
[табличные и переходные тесты](../crates/domain/tests/health_selection.rs).
Контракт: REQ-CORE-004–005, 019–021 и [ADR-0001](adr/0001-connection-core-boundaries.md).

## Входы и выходы

`Health::observe` получает предыдущий volatile snapshot одного транспорта,
типизированное наблюдение и контекст с монотонным временем. Возвращает новый
snapshot и закрытую причину принятия/отклонения. Файлов, сети, часов ОС,
RCI, engine API, секретов и фоновых задач в компоненте нет.

`SelectionStrategy::select` получает неизменяемый `Snapshot` и возвращает
`Decision`: предложенный active, сохраняемое предпочтение, отдельные планы
TCP/UDP, классифицированную причину и разрешение проверок. Реализована стратегия
`StickyHealth`; новые алгоритмы реализуют тот же интерфейс и должны проходить
общие contract-сценарии. Тип протокола отсутствует в ключе оценки и самом
интерфейсе кандидата: capabilities и admission передаются отдельно.

`Intent { enabled, in_pool }` — намерение пользователя. `HealthState` — наблюдаемое
здоровье отдельного транспорта. `ConnectionState` выводит `checking`, `active`,
`standby`, `unstable`, `unavailable`, `draining`, `disabled`, не переписывая intent.
`draining` исключает новые сессии и имеет приоритет отображения даже при уже
выключенном intent. Окончание старых сессий и снятие draining принадлежат адаптеру
и координатору; модель не обещает сохранение сессий при аварии.

## Правила здоровья и времени

- Время — передаваемые монотонные миллисекунды одного epoch. По умолчанию
  `freshness_ms = 90_000`, `failure_window_ms = 300_000`; настройки положительны,
  окно ошибок не меньше TTL. Это defaults чистого алгоритма, а не утверждённый
  бюджет probes/router из #75/#117. Граница TTL включительна.
- Один успех даёт базовое здоровье. Первый отказ даёт `unstable`; затем нужны
  два разных результата `Confirmation` от независимого резервного endpoint.
  Координатор назначает возрастающий `sequence` **до** dispatch; scheduler #75
  обеспечивает независимый endpoint и интервалы. Вызов чистой функции сам
  ничего не проверяет и не ожидает.
- Повторные primary-ошибки не заменяют confirmation. Подтверждённый отказ
  остаётся `unavailable` до успеха либо устаревания данных. Успех сбрасывает
  подтверждение, но не удаляет недавние ошибки. Flapping не делает быстрый
  нестабильный выход предпочтительнее здорового.
- Счётчик недавних ошибок насыщаемый; хранится без неограниченного журнала,
  обнуляется после окна без новых ошибок. Это штраф с окном тишины, не точный
  sliding-window histogram. Задержка сглаживается целочисленным EWMA 3:1;
  при потере свежести сглаживание и незавершённое подтверждение начинаются заново.
- Неверное поколение, повтор/старый ticket, обратный порядок времени, будущее
  и истёкший TTL не изменяют snapshot. Два разных ticket могут завершиться
  в одной миллисекунде. Истёкшее здоровье становится `checking`, не используется
  для выбора резерва и не интерпретируется как подтверждённый отказ VPN.
- TCP и UDP имеют отдельные `Health` и capabilities. `Unsupported` не является
  сетевой ошибкой и не ухудшает TCP. Unknown/unsupported capability не принимает
  положительные probes как доказательство поддержки.

Для общего пула подтверждение унифицировано: первая ошибка + две confirmation
для каждого кандидата. Это сохраняет требование VLESS §4 о подтверждении,
но не переносит shortcut старого shell, где standby мог стать unavailable
после второй обычной ошибки. Shell runtime здесь не меняется.

## Детерминированный выбор

1. Невалидная policy или повторяющийся ID закрывает пути с `InvalidSnapshot`.
   Пустой пул — `Unconfigured`. Пауза или отсутствие включённых участников —
   `Paused`, проверки отключены, предпочтение сохранено, новые пути закрыты.
2. Свежий общий `UpstreamState::Down` закрывает пути и сохраняет предпочтение;
   кандидаты не перебираются. Это классификация общей недоступности от scheduler,
   а не вывод из одного неудачного VPN probe. Неверное поколение/устаревшая
   upstream-проверка даёт `Unknown`.
3. Исправный active остаётся выбранным независимо от latency резервов.
   Первая ошибка удерживает active с `AwaitingConfirmation`. Устаревшие данные
   удерживают только предпочтение, пути закрыты до свежего probe; ложного
   переключения из-за задержавшегося worker нет.
4. Подтверждённый отказ active допускает failover только при свежем `Up`.
   При `Unknown` путь закрыт до upstream-проверки. Явно выведенный, выключенный
   либо лишённый admission active исключается немедленно.
5. Резерв обязан быть enabled/in_pool, admitted, вне draining, иметь Supported
   TCP и свежий успех текущего поколения. Ключ выбора по возрастанию:
   число недавних ошибок, затем более свежий успех, сглаженная задержка, ID.
   Перестановки входного списка не влияют на результат. Числовой предел четырёх
   VLESS не переносится на общий пул.
6. После применения переключения координатор передаёт новый committed active
   в следующий snapshot. Восстановившийся прежний выход становится standby,
   автоматического failback нет.
7. UDP использует только тот же active и только при независимом свежем UDP
   успехе с Supported capability. Иначе `Block`, включая исправный NaiveProxy
   TCP-only; второго активного VPN или скрытого direct для UDP нет.
8. Без пригодного кандидата — fail-closed. `Direct` возможен только при
   `DirectPolicy::ExplicitlyConfirmed` и свежем `Up`, с причиной `DirectFallback`.
   Предупреждение о TCP-only не устанавливает direct policy. Неподтверждённая
   ошибка active или upstream outage не включают direct.

## Обязательства будущего координатора и границы задачи

- Изменение config/capability/admission, disable/enable, pause/resume и restart
  инвалидирует наблюдения: координатор выдаёт новое непереиспользуемое поколение
  и `Health::new(generation)` для TCP/UDP. `Candidate.generation` дополнительно
  блокирует случайно переданное здоровье старой конфигурации. Upstream имеет
  свой snapshot generation. Устаревшие workers не получают новую generation.
- При paused/disabled probes не запускаются, а запоздавшие ответы передаются
  с `probes_enabled = false` либо отклоняются по поколению. Одного сохранённого
  health snapshot недостаточно для возобновления после reboot/pause.
- `admitted` — уже проверенный внешним слоем gate: платформа, DNS/loop,
  предупреждение TCP-only и необходимые операции. Тестовые mixed fixtures
  задают его явно; production `NaiveProxy` adapter продолжает возвращать Unknown
  для TCP и операций. Это изменение не допускает NaiveProxy на реальный роутер.
- `Decision.active` — предложенный выход для новых сессий; `preference` —
  отдельная память выбора. Потребитель не имеет права направлять трафик по
  preference в обход `tcp/udp = Block` или объявлять proposed active применённым.
- Координатор сверяет revisions, выполняет prepare/apply/verify/commit/restore
  и атомарно применяет TCP/UDP/DNS по ADR. Самостоятельная реализация маршрутов,
  DNS, admission UI, probe scheduler, registry, IPC, daemon и locks сюда не входит.
- `opt/`, Makefile и hooks не изменены; текущий supervisor и decision lock #57
  остаются единственным действующим владельцем. ELF не подключён к пакету,
  поэтому изменение `PKG_RELEASE` не требуется. Передача владения — #73/#95/#99.
