# ADR-0001: Единое Rust-ядро, адаптеры и источники состояния

- Статус: принято как целевая архитектура; активация заблокирована gates ниже.
- Дата: 13.09.2026.
- Задача: [#62](https://github.com/ivni/mors/issues/62).
- База проверки: `origin/main`, `533a973` после `git fetch origin main`.
- Область: документация; runtime, пакет и роутер этим ADR не изменяются.

## Контекст

[Контракт #58](../connection-core-requirements.md) требует общего пула,
одного владельца решений, сохранения платформ и постепенного перехода на Rust.
Применимые требования: REQ-CORE-001–018; PRINC-ID в AGENTS.md не заданы.
В актуальном контракте OpenVPN явно исключён: чужие и существующие OpenVPN
не удаляются; миграция использующей его установки останавливается до изменения
рабочего состояния, без автоматического direct fallback.

Проверено чтением кода на базе выше:

| Исходная реализация | Архитектурное следствие |
| --- | --- |
| [vless_runtime](../../opt/bin/libs/vless_runtime): `vless_runtime__with_decision_lock` берёт runtime mutation, затем VLESS decision lock; active preference отделён от runtime state | Сериализацию нельзя потерять при переносе, но shell lock не определяет внутреннее устройство Rust |
| [runtime_lock](../../opt/bin/libs/runtime_lock): owner PID/start identity, токены, cold journal | Одного PID или флага окружения недостаточно для передачи владения; crash recovery остаётся отдельным протоколом |
| [vpn](../../opt/bin/libs/vpn) координирует DNS, интерфейсы и маршруты; [vless-supervisor](../../opt/bin/main/vless-supervisor) выбирает VLESS | Независимый supervisor каждого протокола создал бы конкурирующих владельцев общего маршрута |
| [VLESS §2–3, §11](../vless-architecture.md) закрепляет Xray и Proxy для VLESS | Эти ограничения не являются универсальным data path штатного VPN |
| [Lifecycle §3, §6–7](../lifecycle-architecture.md) задаёт durable intent, staged rollback и порядок locks | Новое ядро должно войти в эти границы, а не обойти их своим daemon |
| [Makefile](../../Makefile), [release verifier](../../scripts/qa/verify-release-artifact.sh), [release workflow](../../.github/workflows/release.yml) поставляют один `all.ipk` | Появление ELF требует явного изменения контракта поставки до включения Rust |

Основание платформенных решений — уже зафиксированные исследования:
[матрица #59](../research/connection-platform-matrix.md),
[Rust spike #60](../research/rust-entware-spike.md),
[Hysteria #61](../research/hysteria2-runtime.md).
Закрытие исследовательского issue не означает прохождения runtime gates.
Здесь эти эксперименты не повторялись.

## Решение

### 1. Один владелец и разделение компонентов

Один долгоживущий Rust-процесс является управляющим ядром. Внутри него один
координатор сериализует изменение управляемого состояния, принятие внешних
ревизий и commit выбора. Worker может параллельно читать или выполнять probe,
но возвращает результат с поколением конфигурации; он не меняет active.
Устаревший результат отбрасывается. Очереди, число workers и deadlines ограничены.
Конкретные численные лимиты определяются измерениями #70/#117.

| Компонент | Владеет | Не имеет права |
| --- | --- | --- |
| Реестр и secret store | ID, тип, membership/enabled, policy, config revision, ownership, secret references, миграции и backup | Выбирать active, выполнять RCI или engine API |
| Health и selection | Производное здоровье, подтверждение сбоя, upstream distinction, чистая функция выбора по snapshot и управляемым часам | Вызывать Xray/Clash/RCI, писать config или самостоятельно применять маршрут |
| Координатор | Очередь команд, transaction/operation ID, revisions, fencing, порядок prepare/apply/verify/commit/restore | Объявлять успех без observed poststate |
| Адаптер протокола/движка | Типизированные validate, discover/read, prepare/apply/verify/restore, probe, drain; перевод в конкретный API | Собственную политику failover/failback, прямые durable записи реестра |
| Платформенный routing apply | Mors policy routes, firewall/ipset, endpoint exclusions, привязку native egress или proxy endpoint | Выбирать победителя, менять чужие объекты или открывать direct без policy |
| CLI и shell-шлюзы | Ввод, подтверждение, запрос, отображение результата по дизайн-системе | Решать по старому snapshot, обходить координатор |
| Observability | Классифицированные результаты операций и агрегаты probes, локальную диагностику и разрешённый экспорт | Управлять выбором или экспортировать произвольные строки backend |

Внутренние адаптеры имеют версионируемый типизированный контракт. Это не ABI
динамических Rust-плагинов: сначала они собираются вместе с ядром; внешний
движок остаётся отдельным процессом с собственным control API. Алгоритм
selection заменяется через чистый интерфейс и общий набор сценариев #70/#74.

```text
CLI / NDM / lifecycle -> запрос -> единственный координатор
                                      | snapshot -> health/selection -> план
                                      | prepare/apply/verify -> адаптеры
                                      | routing apply -> observed route
                                      + commit -> реестр/preference/событие
```

Сохраняются sticky-выбор, подтверждение первой ошибки, приоритет здоровья перед
latency, детерминированные равенства и отсутствие автоматического failback.
Общий upstream failure не запускает перебор всех VPN. Отсутствие выхода
закрывает защищаемый маршрут, кроме явно разрешённого direct fallback.

### 2. Общий пул и capabilities

Запись пула обозначает логическое подключение, а не PID, SOCKS listener или
интерфейс. Охват — VLESS, Shadowsocks, Hysteria 2, WireGuard с отдельно
проверяемыми ASC-вариантами, IKEv1/IKEv2, SSTP, PPTP, L2TP, L2TP/IPsec,
OpenConnect. WAN, модем и VPN-server не становятся выходом по одному имени
или `connected`; клиентская роль и egress проверяются отдельно.

Capability задаётся для `(тип/вариант, OS/компонент, ABI, engine version,
операция)` с основанием проверки и её границами. Обязательные операции:
discover, read, create, update, delete, enable/disable, probe, select,
graceful drain и restore. TCP/UDP, способ изолированного probe, сохранение
неизвестных полей и возможность безопасного read-modify-write — отдельные
свойства, а не следствия наличия типа интерфейса.

- `supported`: есть применимое доказательство операции и успешный preflight.
- `unsupported`: известна конкретная несовместимость/отсутствующий компонент;
  причина и действие пользователя доступны CLI, автоматической установки OS нет.
- `unknown`: данных нет, чтение неполно, версия/схема неизвестна или проверка
  не удалась. Это не `unsupported`, не здоровый резерв и не разрешение mutation.

Обнаружение с read-only capability разрешено даже без create. Однако это не
обещание полного управления: принятие под управление требует доказанных
read/update/restore и жизненного цикла, необходимого REQ-CORE-009.
Синтаксически корректный новый профиль после сетевой ошибки сохраняется как
недопущенный к выбору, отдельно от рабочего выхода.

В работающем пуле **один active для новых защищаемых сессий**. Одновременно
могут жить несколько native-интерфейсов, один Xray для всех VLESS и отдельный
движок Hysteria; standby probes и draining не являются вторым active.
Native VPN использует свой подтверждённый интерфейс и не обязан проходить
через Xray или глобальный Proxy.

Для внешних SOCKS-движков платформенный адаптер предоставляет проверенную
точку входа. Кандидат #61 — один sing-box на Hysteria-профили без автономного
urltest-выбора; VLESS сохраняет один Xray. Общий routing apply выбирает
native egress либо внешнюю точку. Число Proxy для mixed topology и способ
сохранения старых сессий определяются #63/#78/#94; создавать Proxy или процесс
на каждый профиль запрещено. Перенацеливание единственного Proxy на другой
listener не считается доказанным graceful. До доказательства нет скрытого
рестарта: действие, способное разорвать сессии, требует объяснения и явного
подтверждения. Предел четырёх VLESS не переносится на общий пул.

До активации endpoint каждого транспорта исключается из его туннельного
маршрута; bootstrap DNS/upstream path проверяется отдельно. Новый exclusion
добавляется до удаления старого; удаляются только Mors-owned записи.
Непроверенная защита от routing loop блокирует активацию адаптера.

### 3. Источники состояния и границы записи

| Данные | Источник / размещение | Правило |
| --- | --- | --- |
| Membership, policy, принятые настройки, ownership, revisions | Durable реестр Mors | Единственный writer — координатор; secret store отдельно, файлы `0600`, каталоги `0700` |
| Native параметры, которые редактирует Keenetic | Наблюдаемый объект Keenetic плюс последняя принятая revision в реестре | Внешнюю правку принять через reconciliation; копия Mors не даёт права переписать роутер |
| Сгенерированный config движка | Производный от принятого реестра/секретов | Ручную правку не импортировать как новую истину; конфликт диагностировать до замены |
| Здоровье, latency, probe counters, snapshot, locks/PID, очередь работы | Volatile RAM | Потеря при reboot допустима; восстановить как checking/unknown и проверить заново |
| Active preference | Durable ID последнего подтверждённого VPN-выбора | Записать при изменении ID; не переписывать при каждом цикле. В paused/direct/закрытом маршруте это не текущий active |
| Intent/recovery, baseline, backup, schema, итог значимой операции | Durable транзакционные данные | Достаточны для crash recovery; подтверждение записи после durable commit |
| Причинные события и telemetry queue | Bounded durable журнал/очередь по отдельному контракту | Probes агрегируются; batching/переполнение не меняют гарантий потерь без отдельного решения |

Путь `/opt/var/run` сам по себе не доказывает RAM. Физическое размещение,
fsync/rename на целевом носителе, лимиты журнала и допустимые потери определяют
#64/#71/#72/#110/#111/#117/#119. Обычный health-cycle без значимого перехода
не требует durable записи; health snapshot не хранится на флешке. Изменение
active и значимые события могут вызвать запись, даже если инициированы cycle.

Мутация сохраняет intent и необходимый rollback **до** побочных эффектов;
после verify фиксирует commit, preference при изменении и итог операции.
Ошибка durable commit после apply не выдаётся за успех: recovery сверяет
наблюдаемый эффект с intent. На boot незавершённая транзакция восстанавливается
до допуска новых изменений. Preference — только стартовый кандидат:
здоровье старого процесса не восстанавливается как подтверждённое.

### 4. Локальный API запросов и снимков

Целевой транспорт — локальный Unix domain socket в проверенном volatile
каталоге `0700`, доступ root; реализация проверяет peer credentials.
TCP listener, публичный HTTP API и произвольное исполнение shell не входят
в этот контракт. Секретный ввод передаётся закрытым IPC/дескриптором, не argv,
не echo и не общим snapshot. Точная схема и CLI-грамматика — #65/#73/#101.

Минимальная семантика, обязательная для реализации:

| Запрос/ответ | Обязательные поля/поведение |
| --- | --- |
| Handshake | Версия протокола, поддерживаемые операции; несовместимость отклоняется до mutation |
| Command | `request_id`, тип операции, параметры, expected config revision, ожидаемая observed revision затрагиваемого объекта, deadline, требуемое подтверждение |
| Accepted | `operation_id`; означает очередь, а не успешное применение |
| Result / operation query | Стадия, завершённость, классифицированная причина, сохранённое состояние, следующий шаг; успех только после verify/commit |
| Snapshot | `boot_id`, config revision, observed generation, sequence, время наблюдения/возраст, lifecycle state, active transaction, current active, preference, health freshness и capabilities; без секретов |
| Reconcile / probe request | Запрос работы владельцу; ответ чтения не запускает скрытую mutation |

Чтение выдаёт один согласованный immutable snapshot, без записи на диск и
сетевых probes. Клиент видит stale/unknown явно; в `unconfigured`, активной
lifecycle-транзакции и `recovery_required` старые роли не выдаются за работающий
dataplane. Deadlines используют монотонные часы внутри boot, wall clock нужен
для отображения; sequence нельзя сравнивать между разными boot_id.

Повтор с тем же request_id и теми же параметрами возвращает имеющуюся операцию;
другие параметры с тем же ID — conflict. После потери ответа клиент запрашивает
операцию, а не повторяет mutation вслепую. Durable mutators связывают ID с
journal; окно хранения результатов ограничено, после его истечения возвращается
явное неизвестное состояние и требуется reconciliation, а не обещание eternal
exactly-once. Отмена до apply удаляет намерение из очереди; после apply проходит
через транзакционный restore. Timeout клиента не означает откат операции.

### 5. Внешние правки, revision/conflict fencing и rollback

NDM-событие только инвалидирует наблюдение и запрашивает reconcile; периодическое
ограниченное чтение обнаруживает пропущенные события. Адаптер читает управляемые
объекты до plan и непосредственно перед apply. Чужие объекты остаются inventory
до явного принятия. Неполное/ошибочное чтение не означает удаление объекта.

Для управляемого VPN новая полная внешняя конфигурация валидируется и принимается
как новая revision; старое здоровье аннулируется, требуется повторный probe.
Неизвестные поля сохраняются в защищённом snapshot и не удаляются сериализатором.
Если API не позволяет безопасно сохранить их, update становится unknown и
блокируется. Внешнее удаление/disable снимает допуск после подтверждённого чтения;
Mors не воссоздаёт интерфейс автоматически поверх решения пользователя.

План содержит config revision, boot/owner epoch, operation ID, observed fingerprint
и точный write set. Координатор отклоняет stale command, адаптер повторно
сверяет precondition перед эффектом и postcondition после него. Worker старого
epoch не может выполнить новый шаг. Epoch защищает от конкуренции Mors;
**он не является CAS на Keenetic**. Наличие атомарного revision API роутера
не доказано: read-before/write/read-after обнаруживает часть конфликтов, но
не исключает правку между чтением и записью. При невозможности доказать безопасный
field-level update данная mutation остаётся заблокированной до #76/#93.

Rollback сравнивает для каждого затронутого поля/объекта baseline, ожидаемый
poststate операции и текущий observed state. Возвращается только значение,
которое всё ещё совпадает с записанным Mors poststate. Незатронутые поля и новые
внешние значения сохраняются. Созданный Mors объект удаляется только при
доказанном ownership и неизменном fingerprint; чужой одноимённый не удаляется.
Конфликт нельзя исправлять полной заливкой старого RCI snapshot: операция
останавливается с recovery_required и конкретным конфликтующим шагом.
Невозможность восстановления маршрута оставляет безопасно закрытый путь,
без неразрешённого direct. Сохранность внешних изменений должна быть проверена
также при downgrade; старый restore, не понимающий fencing, нельзя запускать
на таком snapshot без совместимого recovery-шлюза (#98/#99).

### 6. Переходные shell-шлюзы

Переход выполняется по компонентам, но владение общим выбором передаётся целиком.
В legacy mode решения принимает действующий shell supervisor; Rust допускается
только для чтения/моделирования. В core mode прежний supervisor остановлен,
его hooks/CLI/NDM направляют запросы ядру, а shell-helper исполняет только
ограниченный шаг координатора. Недоступность ядра не запускает старый выбор.

Передача выполняется под lifecycle/runtime gate: quiesce старого владельца,
проверка отсутствия workers, snapshot, публикация режима/epoch, запуск и verify
нового владельца, commit. Долгоживущие процессы не наследуют временные lock
tokens. Шлюз использует фиксированную операцию, защищённый канал и связанный
с транзакцией scope; произвольный argv/env token не даёт разрешение mutation.

До переноса lifecycle сохраняется порядок lifecycle → test (где применим)
→ runtime mutation → VLESS decision. Lifecycle mutator не получает test lock.
Вызов ядра при удержанном shell lock, который ядро затем пытается получить,
запрещён: gateway передаёт исключительное владение ограниченным шагом и не
запускает конкурирующую mutation. После остановки ядра lifecycle recovery может
стать единственным временным владельцем; это не второй health/selection loop.
Протокол передачи и deadlock/crash-сценарии реализуются в #73/#95/#99.

### 7. Платформенная поставка и update/release

Выбран целевой контракт: **один самодостаточный пакет `mors` на подтверждённый
Entware ABI**, содержащий общую shell-обвязку и соответствующий Rust ELF.
Для нынешних трёх семейств планируются три IPK: MIPS BE, MIPSel, AArch64.
Установка получает ровно один из них; реальные control Architecture и имена
фиксируются по матрице в #67–#69. Это не три одновременно устанавливаемых пакета
и не ELF с `Architecture: all`. Новая подтверждённая ABI расширяет manifest.

Обоснование: один lifecycle/version/rollback unit, отсутствие промежуточного
состояния несовместимых `mors` и `mors-core`, нет расхода места на чужие ELF.
Протокольные движки остаются проверяемыми зависимостями, а не реализацией
Rust-ядра. Их версии/ABI и rollback-совместимость входят в gate поставки.

Кандидат toolchain — patched Rust 1.94.0 и Entware std/GCC/sysroot из #60;
выбор dynamic/static production linkage завершается в #66/#67 после проверки
реальных зависимостей, loader, ресурсов и воспроизводимости. Spike подтверждает
шесть ELF с IPC в QEMU и два MIPSel ELF на NC-1913, но не готовое ядро.
OS минимум — KeeneticOS 5; feed `3.4`/`3.10` не является продуктовым kernel gate.
NC-1913 — доступный физический стенд; для BE/AArch64 используются эмуляция и
явная граница доказательств, без требования приобрести дополнительные роутеры.

**До отдельного внедрения #67–#69/#116 нынешнее правило одного проверенного
`mors_*_all.ipk` в release остаётся в силе. Этот ADR не разрешает его обход.**
Переход должен одним согласованным изменением обновить AGENTS.md, Makefile,
builder ID/manifest/verifier, package/release workflows, release verifier,
updater/preflight, rollback-stub, тесты и документацию выпуска.

Будущий manifest выпуска связывает один source SHA, версию/schema, каждый ABI,
package name/control version, digest/размер IPK, exact builder image digest,
toolchain и runtime dependencies. Публикуются ровно IPK из полной проверенной
матрицы плюс manifest целостности, без дубликатов или скрытого `all` fallback.
QA и все package gates завершаются для того же SHA до immutable tag; процедура
release.yml и explicit version mapping сохраняются.

Updater определяет ABI по проверенному Entware inventory/ELF, не по одному
`uname -m`, и выбирает ровно совпадающий asset. Неизвестный ABI, неполная матрица,
несовместимая схема или отсутствие пригодного rollback блокируют обновление
до quiesce/opkg. Установка `all` → platform package, downgrade обратно и
dependency rollback требуют отдельной проверки opkg #68/#69/#116; это не
предполагается работающим. Старый updater должен получить совместимый путь
перехода до публикации платформенного релиза (#98/#116).

### 8. Observability и секреты

Значимые команды, фазы, выбор и восстановление получают результат и закрытую
классифицированную причину; probes/retries агрегируются. Секреты не входят в
snapshot, argv, ошибки, журналы и telemetry. Экспорт строится по whitelist на
источнике и versioned taxonomy: raw или обратимо закодированные домены, IP,
имена, config, credentials, команды и произвольный stderr запрещены.
Локальный root-only recovery snapshot не является источником экспорта.
Opt-in и purge сохраняют [контракт телеметрии](../telemetry-architecture.md)
и REQ-CORE-015–018; сроки retention и потерь здесь заново не устанавливаются.

## Последствия, альтернативы и оставшаяся работа

Чистая selection-функция тестируется без роутера, адаптер добавляется без нового
владельца выбора. Цена — явные revisions, совместимость IPC, reconciliation,
матрица сборок и сложный переход владения. Rust сам по себе не даёт транзакцию
RCI или graceful: эти свойства требуют отдельных доказательств.

Отклонённые альтернативы:

- Supervisor на каждый backend: конкуренция за общий active и route.
- Selection напрямую вызывает Xray API: алгоритм оказывается привязан к VLESS.
- Все native через Xray/Proxy: необоснованная зависимость и изменение data path.
- Универсальный all.ipk с тремя ELF: лишнее место, скрытый выбор ABI внутри
  пакета; отдельный core-пакет — дополнительная межпакетная rollback-транзакция.
- Health в durable JSON каждый cycle: ненужные записи и ложное восстановление
  свежего здоровья после reboot.
- Полный restore старого RCI snapshot: потеря внешних изменений пользователя.

Следующие границы принадлежат исполнителю указанного issue. Незакрытый gate
блокирует соответствующую **активацию**, но не проектирование и fake-тесты.

| Gate / риск | Работа и критерий закрытия | Безопасное состояние до закрытия |
| --- | --- | --- |
| G1: платформы, ABI, ресурсы | #66–#69/#117: production core + зависимости, IPC/loader/kernel проверки в согласованной матрице, пределы нагрузки | Legacy остаётся рабочим, платформы молча не исключаются |
| G2: mixed routing/transport | #63/#78/#94/#115: TCP/UDP, upstream exclusions, native↔external, drain, отказ во всех фазах | Нет обещания graceful или допуска непроверенного пути |
| G3: внешние revisions | #76/#92/#93: fixtures и race tests read/write/restore, неизвестные поля и внешние delete/edit | Inventory read-only, опасная mutation unknown |
| G4: ownership handoff | #73/#95/#99: CLI/NDM/boot/lifecycle гонки, worker старого epoch, crash и отсутствие двух владельцев | Только один режим с legacy selection |
| G5: durability/privacy | #64/#71/#72/#109–#111/#119: power-loss boundaries, flash writes, journal overflow, secret-marker проверки | Нет ослабления сохранности и экспорта raw trace |
| G6: upgrade/release | #96–#100/#116/#121: all→ABI→rollback, schema, dependency set, matching manifest и gated SHA | Выпуск Rust запрещён до согласованного изменения package contract |

Новые самостоятельные работы сверх этих границ не создаются в #62.
Подробные IPC schemas, алгоритмические настройки, adapter code, runtime
испытания и release implementation остаются соответствующим задачам.
