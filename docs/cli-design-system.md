# Дизайн-система CLI Mors

Этот документ задаёт обязательные правила для новых и изменяемых пользовательских сценариев Mors. Первая полная реализация системы выполняется в командах `mors vless`; остальные команды переходят на неё только при целевых изменениях.

## 1. Основные принципы

1. Сначала показывается итог, затем подробности и доступные действия.
2. Команда без аргументов не выполняет скрытых изменений. Она показывает состояние или открывает явно обозначенное меню.
3. Где возможен выбор из известных вариантов, пользователь выбирает пункт списка вместо ручного ввода.
4. Каждое интерактивное действие имеет однозначный неинтерактивный эквивалент.
5. Опасные действия до подтверждения объясняют последствия и безопасное значение по умолчанию.
6. Ошибка отвечает на три вопроса: что произошло, что сохранилось, что делать дальше.
7. Цвет дополняет текст, но не является единственным носителем состояния.
8. Секреты не выводятся в терминал, JSON, события, системный журнал или диагностический файл.
9. Термины и статусы используются строго по словарю этого документа. Синонимы не вводятся без обновления дизайн-системы.
10. Тихий режим, перенаправление вывода и `--json` никогда не запускают интерактивное меню.

## 2. Информационная иерархия

Диагностический экран строится в следующем порядке:

1. Общее состояние подсистемы.
2. Активное соединение и готовность резервов.
3. Политика безопасного поведения при общей аварии.
4. Последнее значимое событие.
5. Подробности по каждому соединению.
6. Доступные действия.

Пример структуры:

```text
VLESS: РАБОТАЕТ
Активное соединение: Финляндия
Резерв: 2 из 2 готовы
Прямой резерв: запрещён
Последнее переключение: 2026-07-11 14:32, Москва -> Финляндия

1. Финляндия     АКТИВНО       42 мс   проверено 8 секунд назад
2. Германия      РЕЗЕРВ ГОТОВ  57 мс   проверено 6 секунд назад
3. Москва        НЕСТАБИЛЬНО   91 мс   1 ошибка подряд

Выберите соединение или действие:
[1-3] Открыть соединение  [A] Добавить  [P] Политика  [Q] Выход
```

Полная диагностика показывается по умолчанию, но главный вывод всегда остаётся в первых строках.

## 3. Словарь состояний

### 3.1 Состояния VLESS

| Код | Текст | Значение |
| --- | --- | --- |
| `unconfigured` | `НЕ НАСТРОЕНО` | Нет сохранённых соединений. |
| `starting` | `ЗАПУСК` | Xray и supervisor запускаются, данные ещё не подтверждены. |
| `healthy` | `РАБОТАЕТ` | Активное соединение исправно. |
| `degraded` | `БЕЗ ГОТОВОГО РЕЗЕРВА` | Активное соединение исправно, но нет готового резерва. |
| `switching` | `ПЕРЕКЛЮЧЕНИЕ` | Подтверждён сбой, выбирается или активируется резерв. |
| `unavailable` | `НЕДОСТУПНО` | Нет доступного VLESS-соединения и прямой резерв запрещён. |
| `direct_fallback` | `ПРЯМОЙ РЕЗЕРВ` | VLESS недоступен, трафик временно разрешён напрямую явной политикой. |
| `paused` | `ПРИОСТАНОВЛЕНО` | Включена общая пауза или нет ни одного включённого соединения. |

### 3.2 Состояния соединения

| Код | Текст | Значение |
| --- | --- | --- |
| `active` | `АКТИВНО` | Через соединение отправляются новые пользовательские сессии. |
| `standby` | `РЕЗЕРВ ГОТОВ` | Соединение исправно и доступно для переключения. |
| `checking` | `ПРОВЕРЯЕТСЯ` | Результата ещё недостаточно для решения. |
| `unstable` | `НЕСТАБИЛЬНО` | Получена первая ошибка, выполняются подтверждающие проверки. |
| `unavailable` | `НЕДОСТУПНО` | Сбой подтверждён. Соединение исключено из кандидатов. |
| `draining` | `ВЫВОДИТСЯ ИЗ РАБОТЫ` | Новые сессии не направляются, старым разрешено завершиться. |
| `disabled` | `ВЫКЛЮЧЕНО` | Пользователь исключил соединение из проверок и переключения. |
| `invalid` | `ОШИБКА КОНФИГУРАЦИИ` | Сохранённые данные нельзя использовать для запуска Xray. |

## 4. Цвет и терминальная совместимость

- Успех: зелёный плюс явный текст состояния.
- Предупреждение и переходное состояние: жёлтый или существующий предупреждающий цвет плюс текст.
- Ошибка: красный плюс причина.
- Информация и выбранный пункт: голубой плюс текстовый маркер.
- При `NO_COLOR`, неинтерактивном выводе или неподдерживающем терминале смысл сохраняется полностью.
- Управляющие последовательности не попадают в JSON, pipe или файл.
- Ширина экрана не считается фиксированной. Строки не должны требовать терминал шириной 83 символа.

## 5. Меню и ввод

- Числовой выбор применяется для соединений и конечных вариантов.
- `Q` или `q` возвращает назад либо завершает верхнее меню.
- Значение по умолчанию показывается явно.
- Пустой ввод выбирает значение по умолчанию только там, где это безопасно.
- Имя и VLESS-ссылка вводятся вручную, потому что заранее неизвестны.
- Название из фрагмента `#...` ссылки предлагается как начальное, но пользователь может его изменить.
- Имена уникальны. Латинский регистр не учитывается; кириллица и пробелы разрешены, кириллический регистр сравнивается точно из-за ограничений BusyBox locale.
- При неоднозначном имени команда не угадывает, а показывает совпадения и требует ID или точное имя.

## 6. Подтверждения

Подтверждение обязательно для:

- удаления соединения;
- выключения последнего включённого соединения;
- немедленного разрыва сессий;
- добавления, включения или обновления outbound, если для этого требуется перезапуск уже работающего Xray;
- включения прямого резерва;
- замены активного соединения конфигурацией, которая не прошла сетевую проверку.

Неинтерактивная команда не ждёт ввода. Для подтверждения используется явный `--yes`, а для немедленного переключения `--force`. Отсутствие обязательного подтверждения завершает команду без изменений.

## 7. Ошибки и восстановление

Формат сообщения:

```text
Не удалось обновить соединение «Финляндия».
Причина: Xray отклонил кандидатную конфигурацию.
Сохранено: прежняя рабочая конфигурация продолжает использоваться.
Действие: проверьте VLESS-ссылку и повторите команду.
```

Внутренний stack trace, UUID, public key и полный URI не показываются. Технические детали без секретов доступны в подробном статусе и событиях.

## 8. Командный контракт VLESS

```sh
mors vless
mors vless add [--name NAME] [--link URI] [--disabled] [--yes]
mors vless update NAME_OR_ID [--link URI] [--yes]
mors vless rename NAME_OR_ID NEW_NAME
mors vless enable NAME_OR_ID [--yes]
mors vless disable NAME_OR_ID [--force] [--yes]
mors vless activate NAME_OR_ID [--force] [--yes]
mors vless remove NAME_OR_ID [--force] --yes
mors vless pause [--force] --yes
mors vless resume
mors vless list [--json]
mors vless status [--json]
mors vless check [--json]
mors vless events [--json]
mors vless policy direct-fallback on --yes|off
mors vless version
```

`mors vless new` не поддерживается. Команда должна завершаться без изменений и подсказывать `add` или `update`.

## 9. Status, check и exit codes

- `status` отвечает за получение и отображение состояния. Он возвращает `0`, если состояние удалось прочитать, даже когда VLESS недоступен.
- `check` предназначен для мониторинга и возвращает состояние здоровью.
- Ошибка синтаксиса, повреждённое хранилище и недоступность runtime имеют отдельные коды.
- `check` возвращает: `0` для `healthy`, `1` для `degraded` или `starting`, `2` для `unavailable` или `direct_fallback`, `3` для `paused` или `unconfigured`, `4` для неизвестного состояния.

## 10. JSON

- JSON выводится только при `--json`.
- Корневой объект всегда содержит `schema_version`.
- Поля не меняют смысл без увеличения версии схемы.
- Времена выводятся в ISO 8601 и отдельно могут содержать Unix timestamp.
- Задержка хранится целым числом миллисекунд.
- Секретные поля отсутствуют в схеме, а не просто маскируются.
- JSON не содержит цвета, поясняющего текста или прогресс-индикаторов.

## 11. Критерии готовности нового workflow

- Пройдены happy path, empty, loading, degraded, error, recovery и paused состояния.
- Любое изменение можно отменить до записи.
- Неудачное изменение не ломает активную конфигурацию.
- Интерактивный и неинтерактивный пути вызывают одну доменную операцию.
- Вывод понятен без цвета.
- В тестах подтверждено отсутствие секретов.
- Справка, README, changelog и JSON-контракт синхронизированы.

## 12. Глобальные диагностические команды

Диагностические действия не являются синонимами:

- status-подкоманды компонентов читают сохранённое и наблюдаемое состояние без
  активного сетевого доказательства; отдельной top-level `mors status` сейчас
  нет;
- `test` выполняет активную end-to-end проверку DNS, `ipset`, правил
  маршрутизации, тоннеля и внешнего выхода;
- `debug` собирает подробные технические свидетельства для анализа человеком.

Top-level команда `check` не поддерживается. Вложенный `mors vless check`
остаётся частью VLESS health workflow и не заменяет глобальный `mors test`.

Публичный контракт:

```sh
mors test [--all] [--verbose] [--json] [--timeout SEC] [--retries N]
mors test client [--verbose] [--timeout SEC] [--retries N]
mors test --client IPv4 [--verbose] [--json] [--timeout SEC] [--retries N]
mors test cold [--yes] [--verbose] [--json] [--timeout SEC] [--retries N]
mors test cold recover [--yes] [--verbose] [--json] [--timeout SEC]
```

`--all` и `--client` несовместимы. Cold нельзя совмещать с `--all` или
`--client`. Интерактивные `client` и `cold` несовместимы с `--json`; для cold
JSON разрешён только вместе с `--yes`.
`--retries` не применяется к recovery и в этом режиме является ошибкой
аргументов.

Значения по умолчанию: 30 секунд для обычного/client/cold baseline и 90 секунд
для `--all`; допустимый диапазон 10–300 секунд. `--retries` задаёт число
дополнительных попыток сетевого этапа, по умолчанию 1, диапазон 0–5. Timeout
является абсолютным бюджетом probes и интерактивного ожидания. Обязательное
восстановление уже начатой cold-транзакции не обрывается по timeout.

## 13. Состояния и exit codes глобального test

| Код | Текст | Exit | Значение |
| --- | --- | --- | --- |
| `working` | `РАБОТАЕТ` | `0` | Обязательный активный тракт подтверждён. |
| `degraded` | `ДЕГРАДАЦИЯ` | `1` | Основной тракт работает, но часть доказательств или резервов недоступна. |
| `error` | `ОШИБКА` | `2` | Обязательный этап завершился подтверждённой ошибкой. |
| `not_checked` | `НЕ ПРОВЕРЕНО` | `3` | Проверку нельзя достоверно завершить. |
| `unconfigured` | `НЕ НАСТРОЕНО` | `3` | Начальная настройка не завершена; probes не выполнялись. |

Ошибка синтаксиса возвращает `64`. Отсутствующая обязательная runtime
зависимость является `ОШИБКА`, а зависимые этапы получают `НЕ ПРОВЕРЕНО`.
Ошибка активного соединения является `ОШИБКА`; ошибка включённого резерва при
рабочем active path — `ДЕГРАДАЦИЯ`; административно выключенное соединение
нейтрально. Недоступное необязательное evidence при доказанном обязательном
тракте даёт `ДЕГРАДАЦИЯ`, а недоступный обязательный этап — `НЕ ПРОВЕРЕНО`.

В TTY разрешена одна обновляемая строка прогресса, удаляемая перед результатом.
В pipe, redirect и JSON прогресс отсутствует. Human output начинается с общего
итога, затем показывает этапы, причины и безопасные дальнейшие действия.

## 14. Safety и JSON глобального test

Обычный test, `--all` и client не меняют постоянное состояние роутера, не
перезапускают сервисы, не инициируют VLESS failover и не пишут в syslog.
Разрешён только временный localhost-процесс `ss-local`, который гарантированно
завершается и не получает секреты через argv.

`cold` — отдельный изменяющий workflow. Он требует подтверждения, сохраняет
точный snapshot затрагиваемого `ipset` и состояния DNS, а затем восстанавливает
их при любом штатно обрабатываемом завершении. Незавершённое восстановление
блокирует последующие runtime-изменения до успешного
`mors test cold recover`; автоматический широкий `reset` не выполняется.

JSON schema v1 содержит один корневой объект:

- `schema_version`, `command`, `mode`, `status`, `exit_code`;
- `timeout_seconds`, `retries`, `duration_ms`;
- `active_connection` без секретных полей;
- упорядоченные `stages`;
- `connections` или `client` для соответствующего режима;
- `reason_code` и отдельное русское `message`.

Если `--json` присутствует, syntax errors, busy locks, missing dependencies и
ошибки планирования также возвращают один JSON object в stdout; stderr обычно
пуст. IP клиента и внешнего выхода, credentials, полный proxy URI и секреты не
входят в schema и не выводятся в human/verbose output.

## 15. Lifecycle пакета

Установка IPK и запуск диагностических команд не являются согласием на
изменение сети. `postinst`, `mors`, `mors help`, `mors version` и ошибка
синтаксиса не запускают setup, не меняют DNS, firewall, маршруты, сервисы или
пакеты. Команда без аргументов показывает lifecycle-состояние и доступные
действия.

### 15.1 Стабильные состояния

| Код | Текст | Значение |
| --- | --- | --- |
| `unconfigured` | `НЕ НАСТРОЕНО` | Пакет установлен, постоянные сетевые изменения Mors не активированы. |
| `ready` | `РАБОТАЕТ` | Последняя lifecycle-транзакция завершена и наблюдаемое состояние проверено. |
| `recovery_required` | `ТРЕБУЕТСЯ ВОССТАНОВЛЕНИЕ` | Автоматическое восстановление не подтверждено; новые изменения заблокированы. |

Переходное состояние задаётся незавершённой транзакцией, а не подменяет
стабильное состояние. Пользовательский статус транзакции использует тексты
`ПОДГОТОВКА`, `ТРЕБУЕТСЯ ПЕРЕЗАГРУЗКА`, `ПРИМЕНЕНИЕ`, `ПРОВЕРКА`,
`УДАЛЕНИЕ`, `ОТКАТ` и `ВОССТАНОВЛЕНИЕ`.

Единственный источник истины после миграции — lifecycle state. Старый
`SETUP_FINISHED` читается только одноразовой миграцией и затем не участвует в
решениях о запуске runtime.

### 15.2 Командный контракт

```sh
mors setup
mors setup plan [--interface ID --dns dnscrypt|adguard] [--json]
mors setup apply --interface ID --dns dnscrypt|adguard --yes
mors setup resume [--yes]
mors setup recover [--yes]
mors update check [--json]
mors update apply IPK --rollback-ipk PREVIOUS_IPK --yes
mors rollback IPK --rollback-ipk CURRENT_IPK --yes
mors uninstall [--purge] [--yes]
mors uninstall recover [--yes]
```

Интерактивная команда `mors setup` показывает план до первого изменения.
Неинтерактивные изменяющие варианты требуют `--yes`. `resume` разрешён только
для транзакции, остановленной в состоянии `awaiting_reboot`; он не запускается
из shell profile. `recover` восстанавливает конкретный сохранённый snapshot и
не выполняет широкий reset.

До подтверждения lifecycle-команда выводит:

1. планируемые изменения;
2. что будет сохранено;
3. нужна ли перезагрузка или возможно прерывание SSH;
4. команду восстановления.

Старый позиционный вызов `mors uninstall full yes` допускается только как
временный deprecated alias для `mors uninstall --purge --yes` и не показывается
в канонической справке.

Пока локальный cache предыдущего release artifact ещё не гарантирован для всех
legacy-установок, `update apply` и `rollback` требуют явный проверенный rollback
IPK. Каждый artifact сопровождается файлом `.sha256`; отсутствие или
несовпадение digest завершает команду до создания транзакции. После первой
успешной управляемой транзакции rollback artifact хранится вместе со snapshot.

### 15.3 Доступность команд

- `help`, `version` и lifecycle status разрешены всегда и являются read-only;
- `test` в `unconfigured` не запускает probes и возвращает `3`;
- runtime-mutator разрешён только в `ready` и при отсутствии незавершённой
  lifecycle-транзакции;
- `setup resume` и `setup recover` разрешают только соответствующее действие
  над текущей транзакцией;
- в `recovery_required` любые новые изменения завершаются без побочных эффектов
  и указывают точную recovery-команду.

### 15.4 Exit codes и JSON

- `0` — операция завершена или read-only состояние успешно прочитано;
- `2` — операция завершилась ошибкой, прежнее состояние восстановлено;
- `3` — действие сейчас неприменимо: не настроено, busy или требуется recovery;
- `4` — lifecycle state или journal повреждён;
- `64` — ошибка аргументов или отсутствует обязательное подтверждение.

Lifecycle JSON имеет `schema_version`, `command`, стабильный `state`, объект
`transaction` либо `null`, `status`, `exit_code`, `message` и
`recovery_command`. Секреты, содержимое конфигов, endpoint и snapshot в JSON не
входят.

Inventory setup получает интерфейсы только через read-only Keenetic RCI и не
использует старое сканирование с переподключением интерфейсов и временным
NDM-hook. `adguard` доступен в плане только для уже установленного локального
экземпляра с init script и конфигурацией. Первичная веб-настройка или удалённый
AdGuard Home выполняются отдельным workflow и не скрываются внутри setup.

Для VLESS inventory может показать детерминированный управляемый target
`Proxy21 / Proxy21`, даже если сам интерфейс ещё не создан. Такой target
доступен только при уже установленных системных компонентах Keenetic `proxy`,
`opkg-kmod-netfilter` и `opkg-kmod-netfilter-addons`; plan явно помечает его как
требующий provisioning. Подтверждённый setup создаёт только этот интерфейс
внутри lifecycle-транзакции и удаляет его при rollback, если интерфейса не было
до начала операции.

Setup с пустым реестром VLESS разрешён: Xray запускается с локальным SOCKS
inbound и `blackhole` outbound, а VLESS остаётся в состоянии `unconfigured`.
Это fail-closed состояние не считается рабочим тоннелем, но позволяет завершить
настройку dataplane Mors и затем добавить первое соединение через
`mors vless add` без временного обхода lifecycle gate.
